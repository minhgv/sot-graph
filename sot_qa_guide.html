Topic 1: Core Architecture & Physical Grounding

4 Scenarios
Q01
How does sot-graph ensure the knowledge graph accurately reflects the physical state of the filesystem at all times?
RECONCILER DIRTY-CHECK SHA-256
▼

The sot_graph.reconciler coordinator employs a two-tier defense mechanism to capture even the smallest file modification:

  1. Tier 1 - Fast Dirty Check via Filesystem Metadata (O(1)):
    When modifying a line of code, the OS updates st_mtime (millisecond resolution) and typically alters st_size. The Reconciler compares (size, mtime_ms) against file_journal in microseconds.
  2. Tier 2 - Integrity Guard via SHA-256 Hashing:
    If metadata differs, the file content is hashed with SHA-256 (compute_sha256) and compared to file_journal.sha256. If the hash matches (e.g. touch without edits), re-parsing is bypassed.
  3. Atomic Single-Writer Commit:
    All updates for a file (deleting old nodes/edges, inserting AST symbols, resolving references) execute inside a single SQLite transaction, ensuring zero half-committed graph states.
Trigger manual reconciliation CLI
./bin/sot reconcile --workers 4

Q03
How does two-way pending edge resolution work when File A imports a class from File B before File B is indexed?
PENDING-EDGES TWO-WAY-RESOLUTION
▼

In multi-worker environments or large projects, files are indexed asynchronously. When File A imports AuthService.validate() from File B before File B is processed:

  1. sot-graph saves the unresolved link into pending_edges (path, src_dst_symbol, relation, line).
  2. When File B is indexed and exports AuthService.validate, the Reconciler calls resolve_all_pending_edges().
  3. A single SQL query moves pending references into confirmed graph_edges in both forward and reverse directions:
SQL Atomic Two-Way Pending Promotion (`src/sot_graph/db.py`)
INSERT OR REPLACE INTO graph_edges (src, dst, relation, line)
SELECT p.path, n.id, p.relation, p.line
FROM pending_edges p
JOIN graph_nodes n ON n.symbol = p.dst_symbol;

DELETE FROM pending_edges WHERE dst_symbol IN (SELECT symbol FROM graph_nodes);
Q04
Why does sot-graph choose SQLite WAL + FTS5 instead of vector databases or dedicated graph databases like Neo4j?
SQLITE-WAL FTS5-BM25 ZERO-DAEMON
▼

This design choice is rooted in three non-negotiable engineering invariants:

  • Zero External Daemons: No background services, Docker containers, JVM runtimes, or open TCP ports. Runs in-process via standard Python 3.10+ stdlib.
  • Sub-Millisecond Retrieval: SQLite FTS5 (BM25) provides sub-millisecond retrieval (P95 < 1.2ms) without memory-heavy vector embeddings or API token costs.
  • ACID Concurrency via WAL: Write-Ahead Logging (WAL) allows unlimited concurrent readers (AI Agents & MCP clients) alongside a single serialized writer without lock contention.

Topic 2: Self-Healing & Data Integrity

3 Scenarios
Q05
What happens when a file is deleted from disk? How does sot-graph clean up its corresponding nodes and relationships?
AUTO-PURGE CLEANUP REMOVED
▼

When a file is deleted from disk (e.g. rm src/legacy_auth.py):

  1. During reconciliation, the Reconciler detects paths recorded in file_journal that no longer exist on disk.
  2. All nodes whose path matches the deleted file are purged from graph_nodes.
  3. All outgoing and incoming relationships connected to those nodes are deleted from graph_edges.
  4. The journal entry is deleted from file_journal in an atomic transaction.
Query-Time Immediate Purge: If an agent searches before reconcile runs, the Trust Verifier notices the missing path on disk, returns [REMOVED], and cleans the record from the database immediately.
Q06
If a file is renamed or moved to another directory, does sot-graph lose all its connections or create duplicate nodes?
AUTO-REHOME REBUILT
▼

sot-graph implements an Auto-Rehome heuristic based on unique basename matching:

  1. When src/utils/calc.py is moved to src/math/calc.py, the old path is missing.
  2. The verifier scans the repository for a file with the exact same basename (calc.py).
  3. If exactly one match is found, the system issues the [REBUILT] verdict and updates the path in SQLite.
  4. If multiple files share the same name (basename collision), the heuristic safely avoids false updates, marking the old path [REMOVED] while indexing the new path cleanly.
Q07
How does sot-graph guarantee data consistency and prevent race conditions when multiple agents edit files concurrently?
CONCURRENCY SINGLE-WRITER BUSY-TIMEOUT
▼

sot-graph uses a serialized single-writer SQLite architecture configured with high-concurrency PRAGMAs:

  • PRAGMA journal_mode=WAL;: Readers never block writers, and writers never block readers.
  • PRAGMA busy_timeout=5000;: Concurrent writes wait up to 5,000ms for lock acquisition rather than failing with database is locked.
  • generation column: Monotonically increasing generation counters enable optimistic concurrency verification during multi-file transactions.

Topic 4: Graph Analytics & Visualizations

3 Scenarios
Q11
What is God Node detection and how does the 2-hop Blast Radius algorithm work?
GOD-NODE BLAST-RADIUS DIAGNOSTICS
▼

God Nodes are architectural bottleneck symbols whose modification carries high risk across the codebase:

  1. Calculates Mean (μ) and Standard Deviation (σ) of connectivity degree across all graph nodes:
    Cutoff = μ + (threshold_sigma × σ)
  2. Any node with Degree ≥ Cutoff (default threshold_sigma = 1.5) is flagged as a God Node.
  3. 2-hop Blast Radius: Executes a breadth-first search (BFS) exactly 2 hops away from the God Node:
    • Hop 1: Direct callers and dependencies.
    • Hop 2: Upstream services affected indirectly.
Generate God Node & Architecture Report
./bin/sot report --sigma 1.5 --min-size 2 -o ARCHITECTURE_REPORT.md
Q12
What is the significance of community detection (Louvain) and Modularity (Q) / Cohesion Score (C)?
LOUVAIN MODULARITY COHESION
▼

The Label Propagation / Louvain algorithm in sot_graph.analytics automatically partitions files and symbols into Functional Communities:

  • Modularity Score (Q ∈ [-0.5, 1.0]): Measures architectural decomposition quality. Q > 0.3 represents high modularity and clean architectural boundaries.
  • Cohesion Score (C ∈ [0.0, 1.0]): Ratio of internal cluster connections to total connections:
    Cohesion (C) = Einternal / (Einternal + Eexternal)
    If C < 0.4, the cluster is tightly coupled with external modules and represents a candidate for refactoring.

Topic 5: Operations, Maintenance & Performance

3 Scenarios
Q14
How does sot-graph manage concurrency and maintain performance across monorepos containing thousands of files?
THROUGHPUT PERFORMANCE BENCHMARKS
▼

sot-graph processes large codebases at ~24.1ms / 100 files through two optimizations:

  1. Adaptive Worker Threshold: Small batches (< 16 files) run sequentially in the main process to eliminate multiprocessing fork overhead; worker pools are only spawned for large batches.
  2. Zero Daemon Memory Footprint: Embedded SQLite configured with PRAGMA journal_mode=WAL and PRAGMA synchronous=NORMAL keeps RAM footprint below 25MB.
Q15
How do sot clean and sot vacuum work, and why do they include --dry-run modes?
MAINTENANCE SOT-CLEAN SOT-VACUUM
▼

Maintenance commands keep the SQLite database compact and healthy:

  • sot clean: Scans for database paths absent from disk and cleans orphan edges without affecting live nodes.
  • sot vacuum: Rebuilds database pages, defragments B-Trees, and releases unused disk space to the OS.
Safe Maintenance Execution with Dry-Run
# Preview cleanup without mutating database
./bin/sot clean --dry-run

# Execute clean and vacuum with optimization analysis
./bin/sot clean
./bin/sot vacuum --analyze
Q16
How do you verify graph freshness and detect configuration or code drift in automated CI/CD pipelines?
CI-CD DRIFT-AUDIT VERIFY
▼

sot verify provides a strictly read-only, non-mutating integrity audit ideal for CI/CD gates and pre-commit hooks:

CI/CD Pipeline Integration Script
# Execute deep SHA-256 drift check
./bin/sot verify --deep

# Returns exit code 0 on clean state, non-zero on drift
if [ $? -eq 0 ]; then
  echo "✅ Knowledge graph is 100% in sync with disk."
else
  echo "❌ Drift detected! Run 'sot reconcile' before committing."
  exit 1
fi

Topic 6: Edge Cases & Real-World Incidents

3 Scenarios
Q17
What happens when multiple files in different folders share the exact same filename (basename collision)?
AMBIGUITY-GUARD COLLISION
▼

When multiple files share identical names (e.g. src/auth/config.py and src/db/config.py):

  • Physical Indexing: Every file uses its normalized relative path as its unique key in file_journal.
  • Auto-Rehome Ambiguity Guard: When a file is moved, find_rehome_candidate queries for matching basenames. If count > 1, auto-rehome is safely skipped to avoid mapping to the wrong file.
Q18
What happens if a source code file contains syntax errors or invalid characters during reconciliation?
FAULT-TOLERANCE ERROR-HANDLING
▼

During active coding, syntax errors frequently occur. sot-graph isolates errors on a per-file basis:

  1. The worker catches SyntaxError / UnicodeDecodeError, creates a single file node without sub-symbols, and records the parsing error.
  2. Other clean files in the batch continue parsing and commit successfully.
  3. As soon as the developer fixes the syntax error, the next reconciliation updates the file automatically.
Q19
How can an AI Agent document architectural decisions or bug fix notes that do not belong to a specific source file?
SOT-INSERT ADR NOPATH
▼

Agents can persist decisions and guidelines as virtual knowledge anchors using sot insert:

Persist Architectural Decision Record (ADR)
./bin/sot insert \
  --title "Database Concurrency Policy" \
  --body "All transaction queries touching balance tables must use SELECT FOR UPDATE to prevent race conditions." \
  --keywords "database,concurrency,locking,balance"

These virtual nodes receive the [NOPATH] verdict during searches and are preserved across reconciliations.
